## 1. 项目目的与用户偏好

这是一个以天气选择旅行目的地的网站：先选出行日期和偏好（晴天、降雪、细雨、清凉），看全国天气地图，再比较推荐目的地。希望有安全边界，避免推荐极端天气；去过的地方默认从优先推荐中收起，足迹可折叠查看。

用户满意初版视觉，希望逐版打磨。继续沿用现有清爽风格，避免无必要的大改版或迁移框架。

已明确的产品方向：

- 天气始终是主线，景点和旅行内容放在天气详情下方，默认折叠，不做以附近景点地图为中心的产品。
- 推荐优先兼顾省会、代表旅行城市和省份多样性，不能因为某省有很多城市就霸占前排。普通城市仍应可查询，不强制给每个县村写介绍或配图。
- 搜索城市、县镇或村落后，先预览天气，再决定是否保存；不能先保存才能看天气。
- 不喜欢维基百科附近检索，也不希望靠距离排序堆出不相关景点。该方案已经撤下。
- 目前先打磨国内体验；中期考虑亚洲，长期支持全球。海外地名、时区和底图尚未开放。
- 用户已授权将项目上传到自己的 GitHub，并已选择腾讯云 CloudBase 作为网站部署目标，预计初期每天 50 人以内。用户已通过文件上传发布腾讯云测试站，真实接口与交互验收通过；已通过 CLI 登录并部署共享天气函数，未变更套餐或绑定正式域名。
- 用户最新决定：所有地点均不做定时天气刷新，精选 48 点也不预热。后续共享缓存统一按地点、按需更新：访问时复用一小时内的有效数据，仅补缺失/过期点；无人查询不主动回源，并发相同地点需合并更新。此为待实现的新方案，当前 v0.8.1 仍为浏览器直连与本机缓存，共享 PG 实验默认关闭。

2026-11-15 后续进展：搜索索引 gzip 后 889,886 bytes，比源 JSON 2,944,072 bytes 少 69.8%；支持的浏览器首搜优先压缩文件，首屏/空搜索不下载，失败/旧浏览器回退原 JSON。原始覆盖、许可和匹配规则未改变。相同六个查询，本机排序约 20–25 ms 降为 9–15 ms，首次准备字段仍约 0.2 秒，慢设备模拟约 0.8 秒，索引与搜索相关堆增量约 36.9 MiB，不能宣称内存也减少七成。本轮 9 组相关检查通过。

新共享存储仍是验证阶段：现有独立静态桶可通过原测试站分发；临时函数用现有角色直接读写 COS 成功，未调用 PG/天气。禁止覆盖第一次出现双成功，不能作原子锁；APPEND position=0 竞争为 200/409 AppendPositionErr，重放也拒绝，可继续实现条件追加的元数据 CAS。诊断对象/函数已清理，没有角色或套餐变更。下一步实施租约、持久预算、过期接管、跨午夜和失败恢复，再接入前端；不得根据一次原语验证直接打开默认共享路径。

2026-11-15 v0.8.1 恢复查询的历史记录：用户已授权上线并要求修复查询变慢、经常失败。已发布 v0.8.1 到原测试站（sunseek-003）：默认恢复浏览器直连 + 一小时逐点本机缓存，共享 PG 路径仅显式启用。线上真实首屏 48 点三批约 2.54 秒，刷新无新增天气请求，零共享函数请求。脚本缓存版本及旧模块兼容已修复。详见 [恢复与上线记录](weather-query-recovery.md)。此前自动审批额度曾阻止发布，额度恢复后已完成，这不再是当前阻塞。

2026-11-15 成本问题优先：用户最新账单证实约九成消耗来自 PostgreSQL 计算。原先免费 3000 点支持低访问量的估算没有充分计入共享 PG 每个活跃 5 分钟按 0.5 核计量的规则，不能继续沿用。当前上海区价格 342 点/(核·小时)，每个活跃窗口约 14.25 点。功能验收已完成，成本验收未通过；停止反复全库真实验收，优先评估去掉 PostgreSQL 缓存持久层。没有删除数据库、停用后端或升级套餐；随后已发布关闭默认共享路径的静态前端。新增 `scripts/tencent_usage.py` 精简计费明细及离线测试，此脚本不执行 SQL。成本复核、精简账单工具与发布脚本修正一并归档于 v0.8.1。

成本代码复核补充：同一浏览器的本机缓存、同一函数实例的 hot Map 命中均可避开数据库；新实例仍会读取 PG，当前 `claim` 即使全为新鲜数据也会走预算/行锁事务。主要问题是缓存架构与活跃窗口计量不匹配，精简 SQL 只能减少次要开销。不得把一个窗口的价格按每次点击或每个城市乘算。下一方案也不能直接使用 PG 模式 Storage SDK 来宣称零 PG 成本，其元数据/RLS 仍在 PG；应验证真正不经过 PG 的对象或静态文件路径，并等待计费更新确认。此次复核只读取代码、官方规则并做了本地内存探针，没有查询云数据库、回源天气或改动运行中服务。

- `tests/discovery_scope.py` 覆盖冷暖缓存/历史不改变默认结果、全库进度/复用/取消/竞态/限流、大区/省份切换、手机与缓存容量；新增专项及原十组均通过，共十一组。详见 [范围说明](discovery-scope.md)。

### 天气与稳定性

- Open-Meteo Forecast API：默认首次查询 48 个精选地点和已保存个人地点，每批最多 16 个；其余按省份、单地点或主动全库范围查询。
- 请求未来 16 天日级和小时级预报，当前统一 `Asia/Shanghai` 时区。
- 推荐只统计所选活动窗口内的白昼小时，今天已过去的小时不算。保留完整性检查、天气匹配解释、夜间危险天气排除。
- 单次请求超时 22 秒。网络错误、超时、5xx、响应地点数量不符最多自动重试一次；4xx 包括 429 不自动重试。单批超时不再取消后续全部批次。
- 省份显示完整/查询中/获取失败/日期或小时不全的数量，并提供“重试缺失预报”。
- 1 小时内复用真实缓存；更新失败时最多保留 6 小时内缓存。过期或缺失数据不补零，不用示例天气顶替真实预报。
- 2026-11-14 的一次真实浏览器查询：广西 14 点、吉林 10 点都返回 16 天数据，字段无空值。没有复现用户当时的“—”；只能确认并修复批次超时缺陷，不能认定用户原问题必然由它造成。

## 8. 需要保持的边界

- `weather.js` 中降水、降雪和最大阵风采用前一小时累计口径：例如 09:00–10:00 槽使用 10:00 的累计值，瞬时条件用 09:00。不要不经验证改变。
- 不把空值当作 0，不用演示或其他供应商的零散字段拼成“完整真实预报”。
- 不破坏 `sunseek-footprints-v1`、`sunseek-preferences-v2`、`sunseek-places-v3`、`sunseek-weather-v3`、`sunseek-wishlist-v1` 的既有数据。用户数据只在浏览器，不随 Git 上传。
- 临时预览必须不进入持久天气缓存、地点库、推荐和足迹；关闭后迟到的响应不能复活已关闭预览。
- 单日地图预览与整段行程推荐保持区分；采用日期建议才更新主行程。
- 地域多样性要覆盖完整推荐列表，不能只对首页前三名生效。
- 不重新引入附近百科距离列表或让旅游内容盖过天气。
- 不配置精选、全库或省份的定时天气刷新/预热任务。缓存有效期表示访问时判断是否更新，不代表到期就自动回源；页面仅检查过期状态的计时器不发天气请求。
- 开始编辑前检查 Git 状态；按任务范围验证；不改无关功能，不自动开启生产部署。
