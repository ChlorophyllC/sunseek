# 共享天气缓存设计：按地点复用一小时

v0.7.0 设计归档。状态：设计已完成，尚未创建共享后端、数据库、函数或定时任务；当前网站仍使用各浏览器自己的缓存并直连 Open-Meteo。新增后台部署另行执行，不把本文件当作已经接通的服务。

## 核心规则

共享的是**某个地点的一份预报数据**。每个地点在首次成功取回后缓存 60 分钟，所有用户复用该份数据。出行日期、天气偏好、距离、足迹、地图位置等仍在浏览器计算和筛选，不影响共享缓存身份。

全国、华北、山东等视图只决定本次需要哪些地点，不成为共享缓存的存储单位。后端已有的地点不能自动进入用户当前推荐范围。

| 场景 | 后端读取 | 新增上游查询 | 用户页面 |
| --- | --- | --- | --- |
| A 首次看全国 | 默认 48 个精选的逐地点缓存 | 只补缺失/过期地点 | 仍是固定 48 个候选 |
| B 随后展开山东 | 山东已收录地点的缓存 | 扣除前一步已有的济南、青岛等，只补山东缺失地点 | 展示山东的全部收录点 |
| C 随后看全国 | 相同的 48 个精选缓存 | 一小时内可全部复用 | 不因 B 看过山东而增加候选 |
| D 随后看山东 | B 填好的山东地点缓存 | 一小时内通常无需重查 | 展示山东地点 |

例如 A 在 10:10 写入济南，B 在 10:30 写入德州，则济南到 11:10 过期，德州到 11:30 过期。B 读取济南不能把它的获取时间延长到 10:30。不要以整小时桶作 key：10:59 与 11:01 的访问也应复用首次获取后尚未过期的数据。

```mermaid
flowchart LR
    A[全国 / 大区 / 省份视图] --> B[按当前范围确定地点 ID]
    B --> C[最多 16 点一批]
    C --> D[共享天气服务]
    D --> E{逐地点缓存是否新鲜}
    E -->|是| F[返回原始获取时间和预报]
    E -->|否| G[合并同地点的并发查询]
    G --> H[只向 Open-Meteo 查询缺失点]
    H --> I[按地点写入预报与过期时间]
    I --> F
    F --> J[浏览器按个人日期与偏好评分]
```

## 第一阶段覆盖范围

先共享当前目录中的 506 个公开采样点，包括 48 个精选和各省下一级参考点，足以覆盖主要的全国/省份切换。服务端按稳定 ID 从同版本地点目录取坐标，不接受客户端任意改写 provider、变量、单位或查询范围。

个人添加/地图选点/未保存预览暂时继续走浏览器的既有按点查询与缓存；不把个人命名、足迹笔记、收藏、出发偏好上传共享层。后续如果要复用自定义坐标，需单独设计有限范围的坐标规范化和限额，避免无限新坐标打穿上游配额。

## 缓存身份与记录

缓存 key 包括：

- 数据契约版本和预报配置哈希；
- provider、稳定地点 ID，以及该版本实际经纬度（地点坐标改变不能复用旧预报）；
- 时区 `Asia/Shanghai`、单位、小时/日字段集合、16 天覆盖设置；
- 预报基准日期，或等价的覆盖范围检查。

key 不包括用户、设备、地区视图、天气偏好、排序、户外时段、行程子区间和已去过状态。只变这些设置不应再次请求天气。

单条记录建议如下，时间均由服务器产生：

```json
{
  "schemaVersion": 1,
  "cityId": "area-371400",
  "profile": "open-meteo-16d-v1",
  "forecastBaseDate": "2026-11-15",
  "fetchedAt": "2026-11-15T02:30:00Z",
  "expiresAt": "2026-11-15T03:30:00Z",
  "source": "open-meteo",
  "forecast": {}
}
```

`forecast` 保存当前客户端所需的原始字段或无损规范化字段，不保存个人评分结果；不以零补空值。23 时累计边界仍按现有天气引擎规则处理。跨午夜时，旧数据若不含新基准日所需的最后一天，即使未满一小时也应补取，防止前端误报 16 天覆盖。

## 请求流程与并发合并

建议浏览器发送 `GET /api/weather?ids=...`，每批最多 16 个已知 ID，ID 去重排序。后端必须逐地点读取和拼接，不能仅按整个 URL 或整省缓存一份，否则不同组合会重复查询相同城市。

1. 命中新鲜记录直接返回，同时保留各自 `fetchedAt/expiresAt`。
2. 对缺失/过期点取得跨实例的短期互斥锁，再次检查缓存，然后只查询本请求真正需要更新的点。
3. 其他用户碰到同一点正在更新时复用已有结果，或短暂等待/获得 pending 状态；不要再发相同上游请求。
4. 成功校验后仅替换这些点。新数据写入成功后再释放锁；锁有租期，worker 异常后可恢复。
5. 失败不写空预报覆盖有效缓存。保留失败原因、短期失败退避，429 暂停上游队列并遵守可用的 Retry-After。

单实例进程内 Map 只能作热缓存/本实例合并，不能作为跨用户、跨容器共享缓存的唯一实现。持久层需要支持唯一缓存 ID 和原子锁（或事务/条件写）；可用 CloudBase 数据库或适配的持久 KV。缓存的逻辑失效依靠 `expiresAt`，不能假设数据库 TTL 清理会准点发生。

## 响应与现有前端衔接

建议逐地点响应，不以批次返回时间冒充每个点的天气获取时间：

```json
{
  "version": 1,
  "items": [
    {"cityId": "jinan", "status": "fresh", "fetchedAt": "...", "expiresAt": "...", "forecast": {}},
    {"cityId": "area-371400", "status": "pending", "retryAfter": 3}
  ]
}
```

后续接入时把 `requestForecastBatch` 的来源替换为共享客户端，并把服务端 `fetchedAt` 写入 `updatedAt`。不能仍把“收到缓存的当前时刻”写成天气更新时间；否则晚来的用户会把旧数据当成新数据。

- `discoveryPlaces/currentWeatherTargets` 继续确定当前候选；获取到了别省缓存也不扩大全国候选。
- 浏览器保留本机缓存作为快速首屏及网络失败回退。共享层读取失败时避免让所有浏览器无节制地同时回退直连上游。
- 普通用户的“重新获取”重试共享端点，一小时内仍复用共享数据；不开放任意 `force=true` 清缓存，否则每个人都能重新打到上游。管理维护刷新另行鉴权。
- 过期不足 6 小时的数据可按现有失败回退口径显示为“缓存预报”，附真实时间；超过边界则显示不可用，不以演示数据替代。
- 批次 HTTP 缓存最多到这批记录中最早的过期时间；pending/错误不应被长缓存。各地点 TTL 不因读请求重置。

## 腾讯云落地边界

当前测试站是静态应用，浏览器各自的 localStorage 或单纯把整页接入 CDN，都不能完成上面的逐地点并发共享。需要新增共享服务与持久层。

现有天气尝试最多等 22 秒、批次串行。已调研的免费套餐可能固定 3 秒函数超时，实际环境套餐/超时能力尚未读取；不能直接假设慢天气请求放进免费函数就会成功。实现前应核对当前环境能力，再选择足够超时的 HTTP worker，或短函数返回 pending、后台任务填充缓存的异步方式。当前不新建这些资源或升级套餐。

优先按访问需求填充，不持续刷新全部 506 点。48 个精选按每小时一轮最多约 1,152 地点次/天；506 点每小时一轮约 12,144 地点次/天，后者尚未计算字段/天数权重就已超过免费天气接口每日一万的数量级。并发合并之后仍需有全局速率、失败退避和上游配额预算。

共享后端能减少重复上游查询，但会新增腾讯云的缓存读写、计算和出流量，不能直接等同于腾讯云成本也下降。优先验证公共响应能否经 CDN 复用，避免每个新访问者的 48 个点都变成 48 次数据库读取；免费环境是否可给该接口开启合适的加速/缓存能力需实测，不能默认具备。以每天 50 人为初期规模，先从 48 个精选试点，比较上游请求数与腾讯云资源点消耗，再扩展全省按需缓存。

是否需要预热精选，可在真实使用记录后决定；每个访问不到的小时都不刷新，避免为没有访问的地点持续花配额。上游计量依据 [Open-Meteo 定价说明](https://open-meteo.com/en/pricing)，资源点与运行限制见 [腾讯云评估](tencent-cloud.md)。

## 接入前应验收的情形

- 两个独立浏览器看相同地点，只有第一次打上游，显示同一个真实获取时间。
- 两个省份重叠的地点只查一次；全国候选不随任何人的省份浏览改变。
- 大量同时请求同一点，只产生一次上游刷新；worker 超时后锁可释放。
- A 点过期、B 点仍新鲜，仅补 A；新用户读到 B 不延长 B 的 TTL。
- 两种偏好和活动窗口复用同份预报，仍各自计算推荐。
- 午夜覆盖、坐标变更、契约升级不复用错误记录。
- 限流/缺失/错误不覆盖旧数据，回退明确标识且不引发浏览器集体直连风暴。

这些是共享后端的验收要求，并非本轮已经通过的线上功能测试。当前完成的是设计，现有单浏览器缓存和范围隔离测试继续保留。
