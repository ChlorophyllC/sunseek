2026-11-16，北京时间。当前结论：**旧 PG 函数已部署默认拒绝请求的入口，正式网页继续 v0.8.2 直连与本机缓存；累计 PG 费用的具体调用来源仍未查清。** 新 COS 缓存保持关闭，不继续真实天气冷填充或 506 点验收，也没有定时刷新。

`cloudaudit:LookUpEvents` 查询 `ExecutePGSql` 被腾讯云返回 `AuthFailure.UnauthorizedOperation`，当前 CLI 凭据无审计读取权限。请求 ID：`04828530-f170-4dd5-8a54-e92dc58114fa`。没有扩大角色权限、创建密钥或改用其他凭据。环境元数据确认仍为共享 PG；没有为了排查连接数据库或运行 `pg_stat_activity`。

## 已执行的止损措施

只关闭网页实验开关仍保留了可直接访问的旧公开入口。本轮将旧函数部署为默认关闭：

- `SUNSEEK_PG_CACHE_ENABLED` 必须精确等于 `true` 才能继续执行；缺失、`false`、大小写差异都返回 HTTP 410 / `PG_CACHE_DISABLED`。
- 检查位于加载 PG 适配器、创建服务、读取缓存之前，既适用于公开 URL，也适用于直接函数事件。禁用后即使实例曾创建过服务，也不能继续访问它。
- 清单默认值为 `false`。旧部署/建表/SQL 检查/创建 URL 操作现在都需要显式 `--allow-pg`，避免照旧命令意外恢复实验。
- `deploy_weather_cache.py status` 已改为只读 `GetFunction` 配置，不再执行 SQL。原来的数据库计数单独命名为 `db-status --allow-pg`。

13:11 部署完成，读回 `pgCacheEnabled=false`。13:13 用不带任何查询参数的请求验收，实际返回 HTTP 410、`Cache-Control: no-store` 和 `PG_CACHE_DISABLED`，请求 ID `68593050-e17c-11f1-b5d1-5254006d7c73`。即使仍是旧版本，无查询参数也会在 SQL 前返回 400，因此这个验收不会因部署失败而意外查询 PG/天气。

没有删除函数或数据库，没有更换套餐或发布静态网页；旧函数收到请求仍可能产生少量函数调用费用，PG 中保留的数据仍有存储费用。停用检查只能阻止**这条旧函数业务路径**继续访问 PG，不能阻止控制台、其他客户端或平台服务访问数据库，也不能撤回历史费用。

平台级暂停也已核实：HTTP `UpdateTrigger Enable=CLOSE` 返回 `InvalidParameter`；最大独占额度设零返回 `FailedOperation.UpdateFunctionConfiguration`，读回 `ReservedMem=null`。两种操作均未成功，不能将其写成触发器关闭或函数平台暂停。最终采用的是上述已验证的应用入口拒绝方式。

本轮 7 组相关检查通过：停用/显式恢复边界、HTTP 入口、原共享核心、默认浏览器直连及本机复用、静态部署边界、计费摘要与监控解析。天气数据均为本地模拟，没有重新做真实 48/506 点验收；新监控解析也用已有云端响应核对过，正确识别返回范围只到 08:00。
